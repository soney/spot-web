{%- comment -%} Applies the reader's stored theme choice and cycles it when the toggle in _includes/theme_toggle.html is clicked. Inline and blocking, in before the stylesheets, on purpose. The attribute has to exist before the first pixel is painted or a reader whose stored choice differs from their OS preference sees the wrong theme flash. That rules out a deferred external file, and an external blocking one would cost a round trip for ~40 lines. This script is an override, not the mechanism. The stylesheets carry both palettes in light-dark() pairs and follow the OS on their own, so with JavaScript off -- when nothing below ever runs and the attribute is never set -- a reader on a dark OS still gets the dark site. All this adds is the ability to disagree with the OS, and a way back to agreeing with it. The toggle itself hides in that case (the stylesheets key its display off `:root[data-theme]`), so there is no control that does nothing when clicked. data-theme holds the *choice*, not the theme it resolves to. That is what makes "auto" free: the stylesheets already follow the OS by default, so auto needs no rule of its own, and no code here to re-resolve it when the OS flips at dusk -- `color-scheme: light dark` repaints on its own. Storing the resolved value instead would need a prefers-color-scheme listener, and would leave the site unable to tell "dark because they asked" from "dark because it is night", which is exactly the distinction auto exists to keep. {%- endcomment -%}
