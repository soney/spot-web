{%- comment -%} Resolves the light/dark theme and stamps it on as data-theme, which is what the dark-mode blocks in assets/css/site.css and assets/css/cv.css key off. Also wires up the navbar toggle from _includes/theme_toggle.html, if the page has one. Inline and blocking, in before the stylesheets, on purpose. The attribute has to exist before the first pixel is painted or a reader whose stored choice differs from their OS preference sees the wrong theme flash. That rules out a deferred external file, and an external blocking one would cost a round trip for ~40 lines. `data-theme` is always set once this runs -- the CSS never reads prefers-color-scheme -- so there is exactly one thing deciding the theme rather than a media query and an attribute that have to be kept saying the same thing. The consequence is that with JavaScript off the attribute is never set and the site stays light even for a reader whose OS is dark. The toggle hides itself in that case (site.css keys its display off `:root[data-theme]`) so there is no dead control, and light mode is the design the site shipped with rather than a broken state. Restoring the no-JS path would mean a second copy of the whole dark palette behind a media query, which is the kind of duplication that goes silently out of sync. Storing nothing until the reader clicks is what lets `stored()` double as "has the reader chosen?", which is how the OS-preference listener knows whether it is still allowed to follow along. {%- endcomment -%}
